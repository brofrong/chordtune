# ChordTune — дизайн и план

Дата: 2026-09-26

## Цель

Веб-приложение + мобильные приложения (iOS/Android через Capacitor) для гитаристов:

1. **Тюнер** — первая страница, работает офлайн.
2. **Песни с аккордами** — поиск по названию, исполнителю и аккордам; пользователи
   публикуют свои разборы; лайки, рейтинг, комментарии.
3. **Режим «следить за игрой»** — приложение слушает микрофон, распознаёт смену
   аккордов и само прокручивает текст песни.

Десктопная версия — пока просто веб/PWA, нативную обёртку решим позже.

## Стек

| Слой | Выбор |
| --- | --- |
| Монорепо | Bun workspaces + Turborepo, Biome |
| Фронт | Next.js 16 (App Router), React 19, Tailwind v4, shadcn/ui, motion, next-intl (ru/en) |
| Мобильные | Capacitor 8 (iOS/Android), статическая сборка Next.js |

TypeScript 6.x: TS 7 (нативный порт) пока не имеет стабильного JS API, которым пользуется Next.js.

## Структура репозитория

```
apps/
  web/            Next.js: страницы, UI, Capacitor-проекты (ios/, android/)
  api/            Hono + tRPC + Better Auth + Drizzle, свой Dockerfile
packages/
  audio/          DSP без зависимостей от React: YIN, FFT, хрома/аккорды, строи,
                  синтез гитары, AudioWorklet и Web Worker; тесты на реальных записях

  tsconfig/       общие tsconfig
```

Фронт импортирует из `apps/api` **только типы** (`import type { AppRouter }`), поэтому
API можно деплоить отдельно куда угодно (Docker, VPS, Fly).

## Две сборки Next.js

- `BUILD_TARGET=web` — обычная SSR-сборка. Страницы песен рендерятся на сервере
  (скорость первой загрузки, SEO), данные — через tRPC server-side prefetch +
  гидрация TanStack Query.
- `BUILD_TARGET=capacitor` — `output: 'export'` в `out/`, который Capacitor кладёт
  внутрь приложения. Серверных данных нет: те же страницы получают данные на
  клиенте через tRPC. Тюнер полностью офлайн.

Ограничения export-режима, которые надо соблюдать во всём коде:

- нет `proxy.ts`/middleware, нет route handlers, нет `cookies()`/`headers()` в страницах;
- динамические сегменты требуют `generateStaticParams`, поэтому для экрана песни в
  приложении используется клиентский маршрут с id в query (`/song?id=…`), а на вебе —
  SSR-страница `/songs/[slug]`. Обе рендерят один и тот же клиентский компонент.
- локаль в URL (`/ru/…`, `/en/…`) генерируется статически; корень `/` выбирает
  локаль на клиенте.

## Тюнер

### Что улучшаем по сравнению со старой версией

- Анализ уходит из основного потока: **AudioWorklet** захватывает PCM и через
  `MessageChannel` отдаёт его напрямую в **Web Worker**, где крутятся YIN и FFT.
- Исправляется ошибка старого кода: на каждом кадре в кольцевой буфер заново клался
  весь буфер `AnalyserNode`, из-за чего сэмплы дублировались.
- Стрелка и индикатор центов анимируются через `motion` (spring) без перерисовки
  React; React перерисовывается только при смене ноты или струны.
- Размер окна анализа зависит от инструмента (бас требует 4096 сэмплов для E1).

### Функции первой версии

- Инструменты и строи: гитара (Standard, Drop D, Open G, DADGAD, Half-step down),
  бас (4 струны), укулеле. Выбор сохраняется в `localStorage`.
- Автоопределение ближайшей струны выбранного строя; струна помечается
  «настроена», если держится в ±3 центах ~0.6 с.
- Эталонный звук струны по нажатию (синтез Karplus–Strong из старого проекта).
- Отладочная панель (волна, спектр, YIN) за переключателем; worker считает
  отладочные данные только когда панель открыта.

## Формат песни (черновик грамматики)

```
{title: No Smoke Without Fire}
{artist: Example}
{key: Em}
{tempo: 90}
{time: 4/4}
{capo: 0}

[Verse 1]
|${Em}No smoke without|${Em} fire|
|${G}No silence if there's|${G} no sound|

[Instrumental]
|${Em}|${C} ${D}|
```

Правила:

- `{key: value}` в начале файла — метаданные.
- `[Название]` на отдельной строке — начало раздела (куплет, припев, проигрыш).
- `|` — граница такта. Строка с тактами — последовательность тактов.
- `${Chord}` — аккорд, привязанный к позиции в тексте. В такте может быть несколько
  аккордов. Такт без текста — инструментальный.
- Аккорд: `root[#|b] quality? (/bass)?`, например `${F#m7/C#}`.
- Строки без `|` и `${…}` — обычный текст (комментарии, заметки).

AST:

```ts
type SongDoc = { meta: Record<string, string>; sections: Section[] };
type Section = { label: string | null; lines: Line[] };
type Line = { kind: 'bars'; bars: Bar[] } | { kind: 'text'; text: string };
type Bar = { segments: { chord: Chord | null; text: string }[] };
```

Из AST строится плоская «лента» аккордов `{ chord, sectionIndex, lineIndex, barIndex }` —
по ней работает режим «следить за игрой». Такты дают естественную единицу
синхронизации, поэтому формат с `|` для этой фичи удобнее, чем чистый ChordPro.

Храним исходный текст; AST строится при чтении, а в БД дополнительно
денормализуется массив уникальных аккордов для поиска.

## Данные (фаза 7+)

- Таблицы Better Auth: `user`, `session`, `account`, `verification`.
- `artist` (id, name, slug).
- `song` (id, slug, title, artistId) — «что за песня».
- `arrangement` (id, songId, authorId, content, chords text[], key, capo, tempo,
  status draft/published, createdAt, updatedAt) — конкретный разбор аккордов от
  пользователя. У одной песни может быть несколько разборов.
- `arrangement_like` (userId, arrangementId) — лайки.
- `arrangement_rating` (userId, arrangementId, value 1–5) — «насколько точно».
- `comment` (id, arrangementId, authorId, parentId?, body) — комментарии, один
  уровень вложенности.

Поиск: `pg_trgm` + full-text по названию/исполнителю; фильтр «песни только из этих
аккордов» через `chords <@ ARRAY[...]` с GIN-индексом.

## Режим «следить за игрой» (фаза 10)

1. Worker считает хромаграмму и кандидатов аккордов (`packages/audio`, уже есть база).
2. Онлайн-выравнивание по ленте аккордов: HMM/DTW, где состояние — позиция в
   ленте, переходы «остаться / следующий / пропуск», вероятность наблюдения —
   сходство хромы с шаблоном аккорда.
3. UI подсвечивает текущий такт, аккорды отображаются над текстом, плавная
   автопрокрутка.

## Статус (2026-09-26)

Фазы 0–5 сделаны. Что выяснилось по ходу:

- В старом анализе автоусиление поднимало шум перед атакой, YIN выдавал на нём
  суб-октаву, и трекер держал её до ~0.4 с. Исправлено шумовым гейтом до усиления
  (адаптивный уровень шума) и правилом «шаткая фиксация уступает уверенному кадру».
  Точность по записям открытых струн — 94–100 % кадров.
- AudioWorklet грузится через Blob URL (бандлер копирует worklet-модули без
  транспиляции); Web Worker Turbopack собирает сам.
- `noUncheckedIndexedAccess` выключен в `packages/audio` и `apps/web`: веб
  проверяет исходники пакета, а в DSP-циклах флаг даёт только шум из `!`.
- Better Auth 1.7 поддерживает Drizzle relations v2 через
  `@better-auth/drizzle-adapter/relations-v2`; схема сгенерирована их CLI.
  Для Capacitor включён bearer-плагин, токен хранится в `localStorage`.

## Риски

- **Cookies Better Auth в WebView** Capacitor (origin `capacitor://localhost`) —
  вероятно, понадобится bearer-плагин Better Auth для нативных сборок.
- **AudioWorklet в Next/Turbopack** — если бандлер не соберёт worklet через
  `new URL(..., import.meta.url)`, собираем его `bun build` в `public/`.
- **Drizzle 1.0 RC + адаптер Better Auth** — проверить совместимость, при
  необходимости держать схему auth вручную.
- **Микрофон на Android WebView** — Capacitor пробрасывает `RECORD_AUDIO` через
  `WebChromeClient`, но нужно проверить на устройстве.
